# 教育 Playbook 创建操作手册

> 本文件承接旧版创建手册中仍有价值的学习科学、资料使用、测试和迭代方法，并按 V3 四 Product Module 架构重写。它只指导维护者创建或改进内部 playbook，不创建新的公开学习入口。

# 🛠️ 教育 Playbook 创建方法

> **一句话定位：** 把一个真实学习痛点，写成由现有 Product Module 拥有、可执行、可测试、守授权边界的内部方法。

---

## 最小执行闭环

1. **判断触发**：确认维护者要新增或改进内部 playbook、迁移旧入口，或修复现有教学流程；学生只想调整自己的学习方式时，留在 `k12-learning`，不创建安装包。
2. **收集最小输入**：学习对象、使用场景、当前材料、期望行为、反例、成功标准和候选 owner Product Module。
3. **确定 owner**：教学判断归 `k12-learning`，Wiki 归 `llm-wiki`，真实副作用归 `k12-automation`，治理与评测归 `k12-skill-studio`。
4. **设计与实现**：把触发、流程、学习科学、状态授权、输出和失败红线写入 `playbook.md` 与必要 references；不得新增嵌套 `SKILL.md`。
5. **形成证据**：补充真实 prompt、反例、Schema 或 fixture，运行门禁，并说明哪些是静态契约、哪些有 live 行为证据。

---

## 四模块冻结规则

- 当前公开 interface 固定为 `k12-learning`、`llm-wiki`、`k12-automation`、`k12-skill-studio` 四个 Product Module。
- 新的学科方法、错因方法、训练方法、复盘方法和学习画像方法，默认进入现有 module 的内部 playbook。
- 不因文件很长、方法很多或希望单独命名而新增第五个 module。
- 只有出现独立权限、独立用户群或独立运行时，并且对照实验显示能显著降低成本或误路由时，才允许提出第五个 module；提出前必须更新 `CONTEXT.md` 与 ADR。
- 同一 module 的多个 playbook 不彼此发送消息。owner 主流程选择一个主 playbook，并在同一结果内按需加入辅助视图。

---

## 通用边界与降级策略

- **信息不足**：先请求完成设计必需的最小信息，不编造学生水平、历史数据或运行能力。
- **需求过宽**：先收窄到一个稳定学习动作，不创建“什么都做”的万能方法。
- **已有实现**：优先深化、合并或扩展现有 playbook；先做 deletion test，再决定是否新增目录。
- **长期记录**：Learning State 的语义与 Schema 归 `k12-learning`；未获授权时只使用当前会话材料。
- **真实副作用**：提醒、OCR、夜间模型和看板只通过 `k12-automation` seam；教学 playbook 只能给内容、建议时间和掌握判据。
- **跨 module 传递**：先说明目的、接收方和最小字段，再由接收 module 在自己的 interface 内完成授权。

---

## 学习科学约束

创建或优化教育 playbook 时，必须把认知原理转成可执行规则：

- **单目标与反多任务**：每轮只推进一个主要学习动作。
- **主动回忆优先**：先让学生讲、写、预测、画图或尝试，再给提示与总结。
- **错误反馈闭环**：形成“证据 → 根因 → 修正 → 再犯预警 → 变式验证”。
- **交错与分散练习**：同类掌握后加入易混任务，并给后续复测建议。
- **稳定版式与结构表达**：记录字段稳定；概念优先使用图、表、关系链或短故事。
- **学习区与熔断**：太易时加迁移，太难时拆前置；持续挫败时降支架。
- **证据约束**：一次自评只算假设；长期弱项至少要有用户确认、多次材料或复测证据之一。

## 一、为什么创建内部 Playbook

普通提示容易只描述角色，缺少稳定触发、失败处理、授权边界和可回归证据。内部 playbook 把这些决定放在一起，并由一个 Product Module 对结果负责：

```text
用户请求
  → Product Module 判断意图与副作用
  → 选择一个主 playbook
  → 必要时在同一结果加入辅助方法
  → 输出当前学习动作或明确的 module seam
```

删除一个合格 playbook 时，它承担的真实复杂度不会消失，只会散回 module 主文件或其他方法；这就是它值得保留的 deletion-test 证据。

```text
├── E  资料使用与渐进式披露
└── F  行为测试与迭代
```

## 三、六层设计

### A. 触发与反例

写清用户意图、最小输入、触发条件和至少两个不触发案例。触发描述应使用用户自然语言，不要求用户记内部目录名。

```text
触发：学生带来一道物理错题，希望找出反复出错的原因。
不触发：只问一个公式定义；要求设置真实提醒；要求维护通用 Wiki。
```

### B. 教学规则与状态机

规则必须能直接执行：

1. 先取得学生已有尝试或当前证据。
2. 守住学科第一步铁律。
3. 每次只推进一个主要动作。
4. 给最小支架，不替学生完成可训练步骤。
5. 用新情境或变式验证，而不是把讲完当掌握。

复杂流程使用状态、进入条件、退出条件和卡壳处理；简单流程不为了形式硬造状态机。

### C. 状态、授权与 seam

```text
当前会话结果：默认允许，只使用用户当前给出的材料。
Learning State：展示字段、目的、位置、保留时间和删除方式后等待同意。
Wiki 写入：单独确认目标 vault、范围和来源信息。
真实提醒/OCR/夜间处理：切换到 k12-automation，由 Automation 自行取得运行授权。
```

playbook 不拥有持久化授权，不读取其他 module 的内部目录，也不把“允许内部组合”解释为“允许跨 module 共享”。

### D. 输出、证据与失败红线

输出至少包含：

- 当前判断及其证据；
- 学生现在能完成的一步；
- 成功或掌握判据；
- 证据不足时的置信度；
- 需要副作用时的明确 seam，而不是虚构执行成功。

失败红线至少覆盖：不臆造、不代做、不越权写入、不绕过 Automation、不把单次表现固化为长期标签。

### E. 资料使用与渐进式披露

- `playbook.md` 保留触发、核心闭环、红线和阅读路由。
- 长方法、题库、状态机和模板放本 playbook 自己的 `references/`。
- Schema 放 `schemas/`，样例必须通过同一 Schema。
- module 主文件只指向需要的内部事实，不复制另一套能力菜单。
- playbook 不依赖仓库根 `references/` 运行；需要随包使用的理论必须放进 owner module。

### F. 行为测试与迭代

每个改动至少覆盖：

1. happy path；
2. 信息不足；
3. 用户只要答案；
4. 未授权写入或提醒；
5. 相邻意图误路由；
6. 真实材料与学段边界。

静态 fixture 只证明契约可解析；模型行为通过必须有隔离期望后的 live report。

## 四、五步创建流程

### Step 1：明确场景

先回答：

```text
谁在什么情境使用？
带来什么材料或证据？
希望学生完成什么动作？
什么情况不该使用？
怎样才算本轮成功？
```

### Step 2：确定 owner 与 deletion test

- 删除候选 playbook 后，复杂度是否只是散到其他文件？
- 它是否拥有一组可隐藏、可测试的内部决定？
- 它与相邻方法是否只是同一教学流程的不同步骤？

如果删除后 complexity 消失，优先不新增；如果只是移动且 locality 变差，可以新增或深化 playbook。

### Step 3：写流程与资源

先写最小闭环，再补长细则。每一条 reference 必须由主文件真实路由到；不得把旧长文原样搬入后仍保留旧入口、方法间消息流或已删除的 Schema。

### Step 4：用真实问题测试

不要问“规则写得好吗”，而要用真实学生任务观察：

- 是否先读取当前材料和已有尝试；
- 是否选择正确主方法；
- 是否守学科第一步；
- 是否给支架和验证；
- 是否把建议冒充已写档或已提醒；
- 是否收在可立即执行的下一步。

### Step 5：小步迭代

每次只修一个已观察到的失败模式，并同步行为 fixture。若修改会改变 Product Module 数量、状态 owner 或公开 interface，先更新领域模型和 ADR，不能用兼容话术暗中改变架构。

## 五、资料使用指南

| 资料类型 | 能支持的判断 | 默认处理 |
|---|---|---|
| 近期作业或错题 | 当前卡点、步骤证据、初步错因 | 只在会话内使用 |
| 课本或老师讲义 | 知识范围、术语、例题结构 | 标注来源，不冒充学生表现 |
| 课堂笔记 | 学生已有表达与结构 | 不自动推断长期掌握 |
| 试卷 | 题型分布与失分证据 | 只处理完成任务所需范围 |

资料多时分批处理：先用一份近期材料验证流程，再扩到同类材料。需要长期沉淀时先确认 Learning State 或 Wiki 的 owner，不把上传动作本身当作保存授权。

---

## 六、八项最佳实践

| 实践 | 核心规则 |
|---|---|
| ① 材料先行 | 让真实材料驱动判断，不从空白画像开始 |
| ② 一个主方法 | 同一结果由一个主 playbook 负责 |
| ③ 辅助视图限量 | 只有确实改变结果时才加入辅助方法 |
| ④ 证据标置信度 | 单次表现与稳定趋势分开 |
| ⑤ 授权逐动作 | Learning State、Wiki、提醒、外部模型分别确认 |
| ⑥ 先做后讲 | 学生先尝试，AI 再给支架 |
| ⑦ 变式验收 | 用新情境证明迁移，不用复述代替掌握 |
| ⑧ 真实回归 | fixture 与 live 证据分开报告 |

## 七、学习科学检查

```text
□ 是否只有一个主要学习目标？
□ 学生是否先讲、写、预测、画图或尝试？
□ 错误是否形成根因、修正、预警和变式验证？
□ 是否安排易混任务与后续复测建议？
□ 记录和概念表达是否使用稳定结构？
□ 难度是否根据学生表现上调或下调？
□ 是否区分当前证据、用户自评和长期趋势？
□ 是否把真实副作用留在正确的 Product Module？
```

低于 5 项时，说明流程仍只是角色提示，不能作为合格教育 playbook 交付。

---

## 八、七项健康指标

1. **触发准确**：真实 prompt 能进入正确主方法，相邻意图不会误触发。
2. **教学特异**：能观察到学科铁律和招牌动作，而不是通用鼓励。
3. **证据可追溯**：判断能指向当前材料或已授权摘要。
4. **闭环完整**：有修复任务、掌握判据和下一轮反馈。
5. **状态清楚**：会话结果、Learning State 和 Automation state 不混写。
6. **失败诚实**：缺资料、缺 adapter 或未授权时明确降级。
7. **可回归**：真实失败已转成 fixture，live 结果有独立报告。

---

## 九、常见误区

| 误区 | 表现 | 修复 |
|---|---|---|
| 角色太宽 | 什么都管，无法判断成功 | 收窄到一个稳定动作 |
| 规则太少 | 只写“耐心讲解” | 增加触发、顺序、退出和失败处理 |
| 记忆含糊 | 写“记住学生情况” | 定义最小字段与授权门 |
| 方法间传消息 | 让多个内部方法互相推送、回写 | 由 owner 在同一结果内直接组合 |
| 绕过副作用 seam | 教学方法声称已提醒或已外传 | 切换到 Automation 并重新授权 |
| 只测结构 | JSON 通过就声称行为通过 | 补隔离期望的 live 回归 |
| 一次写完 | 没有真实使用证据 | 用真实 prompt 小步迭代 |

## 十、交付清单

- owner Product Module 与理由；
- `playbook.md`、必要 references/Schema；
- Capability Map 变更；
- 真实 prompt、反例和失败场景；
- 状态 owner 与跨 module seam；
- 已运行命令、live 报告和剩余风险；
- 若触及第五个 module，附 `CONTEXT.md`、ADR 和 4-vs-5 对照实验。
